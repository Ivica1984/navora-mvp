### Ask 1 · Region from the postcode at intake (row po 07:39; `eng` #1177)

- **Settled on the code reading of `eng` #1177 (IMPLEMENTED as reading, not verified by me in code):** intake stores no postcode today; `cases.plz` exists but no command writes it; the case already carries `residence_canton` (required by readiness, used for residual financing and tariffs).
- **Data minimisation, postcode alone:** a postcode of an identifiable client's place of care is personal data in combination (as at 04:23, Ask 3). Collecting it **only** to derive a region is **not** minimal when a field NAVORA already holds gives the same result: on `eng` §2, `residence_canton` maps one to one to BS/BL for the pilot. So, in order of protection:
  - **(R-a) most protective:** derive or check the region from data already held (canton; or for a ward, the home's region set once). No new datum. Compliant with DSG Art. 6 Abs. 2 under every plausible interpretation, Phase A and real data, **subject to (R-c)**.
  - **(R-b)** a postcode field is proportionate only if NAVORA needs the place-of-care address for the care itself (the visit), and then reuses it (P-a to P-e, 04:23). Never a postcode collected for routing alone.
- **(R-c) Purpose and accuracy caveat (new):** `residence_canton` is the **legal residence** for residual financing; the region a search needs is the **place of care**. They can differ (a client resident in one canton cared for temporarily at a relative's in the other). Using the residence canton for routing reuses a datum for a related purpose (DSG Art. 6 Abs. 3, as cited: compatible, in my reading) but risks an inaccurate result (Art. 6 Abs. 5, as cited) and a mis-routed search. Protective design: the derived region is **shown with a one-tap correction, never silent** (as the PO row says), the override has an audit row (from, to, who, when; no reason text with health content), and the residence canton is never changed by a routing override. Whether a residence/place-of-care difference is a patient-safety hazard is `cra`'s question.
- **FE-019 boundary cases:** on [O3] a postcode can cover several localities and a locality several municipalities; the directory gives a canton code per locality. Whether any postcode spans BS and BL is **UNKNOWN** (not checked). Protective rule if a postcode table is ever built (matches `eng` §4): an ambiguous postcode returns «nicht eindeutig» and requires a pick; never a silent default to one canton.
- **Source and licence (`eng` §3):** [O1] and [O2] show **different terms for the same dataset** (commercial use with permission vs. open use with source).
