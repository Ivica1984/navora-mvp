# D-26 — Service-role key on the app server for invitations

## Decision summary
May NAVORA's app server hold the Supabase service-role key so that an invitation recorded in `/admin` also creates the invited person's Auth account and sends the invitation e-mail (Supabase Auth admin invite), instead of a NAVORA operator creating each account by hand in the Supabase dashboard? **PO working view, not a decision:** yes, on the server only, for the invite call alone (one server action, never in a client bundle, never for data reads), rate-limited and audited, with the key in the hosting provider's secret store and a rotation date, and **only in staging** until D-1 (live project) and D-2 (hosting) are settled. **Preliminary route:** a reversible technical choice the PO may decide once Engineering confirms the isolation and `lca` finds no privacy issue; holding a production secret and setting it on a live host stays the owner's action (COORDINATION rule 5). Inputs requested: Engineering, Legal & Compliance. No clinical input needed (no care rule; the qualification part belongs to D-29).

## Context and problem statement
- **IMPLEMENTED (ADM1, migration 0035, ADR-046):** `public.member_invitations` (email, role, display name, optional team and qualification, 14-day expiry, revocable, audited by trigger); `accept_my_invitations()` creates memberships on the first sign-in with the **confirmed** e-mail (`auth.users.email_confirmed_at`). Sign-up is disabled (`supabase/config.toml` `enable_signup = false`); the app holds only the anon key. A search of `src/` and `supabase/` finds no use of the service-role key (read 2026-10-24, not tested).
- **What it blocks:** invitations end in a manual dashboard step by a NAVORA operator. PO 2026-10-22 20:15 accepted this as an ADM1 deviation for a pilot of a few teams. It does not scale, and it blocks **D-20** (teams admit colleagues themselves): a team cannot invite a colleague if only a central operator can create the account.
- **Care-model relevance:** a central back-office step between a team and a new colleague is exactly the coordination layer the model removes (value 4, team autonomy; value 5, administration). It also delays cover: a nurse who joins a team cannot be planned until an operator acts.
- **Safe default in force:** no service-role key in the app; accounts created by hand; the invitation assigns role, team and qualification on first sign-in. A qualification on an invitation is a label, not verified evidence (D-29 default).

## Options considered
| Option | What it means | For | Against |
|---|---|---|---|
| A | Keep manual account creation (status quo) | no privileged secret on the server | central operator step; blocks D-20; slow onboarding |
| B | Service-role key on the server for the invite call only (`auth.admin.inviteUserByEmail`), behind an admin (later: team) permission check, rate-limited, audited | removes the operator step; small change; reversible (remove the key) | a privileged key on the app host: a server-side flaw could misuse it beyond invitations |
| C | A Supabase Edge Function holds the key and exposes only "invite this open invitation id"; the app calls it with the user's JWT | the key never reaches the Next.js host; the function checks the invitation row in the database | one more deployable; needs staging (D-2) to run hosted |
| D | Enable e-mail sign-up restricted to invited addresses (a database hook refuses sign-up without an open invitation) | no privileged key at all | sign-up hooks and their failure modes to confirm (`eng`); the e-mail still comes from Supabase Auth templates |

## Engineering impact
*requested 2026-10-24 (po).* Asked: (1) whether C or D is feasible on the current Supabase plan and stack, and their cost compared with B; (2) for B, how the key is kept out of client bundles and logs (server-only module, build check), and whether a single server action can be the only importer; (3) the audit record for each invite call (who, which invitation, result) and a rate limit per organisation; (4) whether the invite works in CI without a real mail sender (local Inbucket/Mailpit), so an e2e can cover it; (5) the rotation procedure and who performs it (owner, rule 5); (6) reversibility: what remains if the key is removed (fall back to A).

## Clinical impact
not needed: no care, documentation or safety rule. The qualification carried on an invitation stays an unverified label until D-29's real-data gate; this package does not change that.

## Legal/compliance impact
*requested 2026-10-24 (po).* Involved because the invite sends an e-mail to a person who has not yet agreed to anything (staff personal data: e-mail address, name, role; not health data), because a processor (Supabase Auth, its mail sender) processes it, and because a privileged credential is a data-security measure (DSG Art. 8). Asked: (1) is sending an invitation e-mail from NAVORA, recorded by an administrator (later a team member), compliant under every plausible interpretation, and what must the e-mail and the first sign-in tell the person (information duty, DSG Art. 19); (2) does any option change the processor or transfer position already examined for D-2 (Supabase Pte. Ltd, SCCs); (3) is holding the service-role key on an EU app host a data-security question the owner must approve, or a technical measure within the PO's authority; (4) how long an expired or revoked invitation (e-mail address of a person who never joined) may be kept (link to D-4's provisional rule).

**Sources (read 2026-10-24 in this run unless marked):**
- [I1] DSG Art. 19 Abs. 1-5, as reproduced in Glatthaar/Schröder, Onlinekommentar zu Art. 19 DSG (onlinekommentar.ch, Stand 20 August 2023; not an official publication): duty to inform also when the data are not collected from the person (Abs. 1); at least identity and contact details of the controller, purpose, recipients or categories of recipients (Abs. 2); if not collected from the person, also the categories of data (Abs. 3); for a disclosure abroad, the state and the Art. 16 Abs. 2 guarantees or the Art. 17 exception (Abs. 4); if not collected from the person, at the latest one month after receipt, but **at the latest at the moment of disclosure** if the data are disclosed earlier (Abs. 5). The commentary reads disclosure to a processor (cloud storage) as such a disclosure, so the one-month period rarely helps and information is in practice due at once.
- [I2] DSG Art. 20 Abs. 1-2, as reproduced in Glatthaar/Schröder, Onlinekommentar zu Art. 20 DSG (Stand 20 August 2023): no duty if the person already has the information (Abs. 1 lit. a), the processing is provided for by law (lit. b), and others; for data not collected from the person, also if informing is impossible or disproportionate (Abs. 2).
- [I3] DSG Art. 8 Abs. 1-3, as quoted on law.ch, "Grundsatz der Datensicherheit" (secondary; last modified 12 December 2023): controller and processor ensure risk-appropriate data security by suitable technical and organisational measures; the measures must make it possible to avoid breaches; the Federal Council sets minimum requirements (DSV). **The DSV Art. 1-3 text was not readable in this run** (the copies found were the old VDSG or a cantonal ordinance).
- [I4] EDÖB, *Technische Empfehlungen für die Protokollierung gemäss Art. 4 DSV*, version 1.0, 15 September 2023 (edoeb.admin.ch): for private controllers, logging of at least storing, changing, reading, disclosing, deleting and destroying is required where sensitive data are processed automatically **on a large scale** and preventive measures cannot ensure protection (Art. 4 Abs. 1); a log shows who, what kind, when, and the recipient (Abs. 4); kept at least one year separately from the system, accessible only to those who check data protection or data security (Abs. 5); logs may not be used to monitor users' behaviour (section 1.3).
- [I5] datenrecht.ch, "Änderungen der DSV auf den 1. Dezember 2025" (secondary synopsis, PDF): Art. 4 gains Abs. 2bis (the review of logging under Abs. 2 is done in writing and given to the EDÖB on request) and Art. 46 transitional periods (review by 31 December 2026, logging implemented by 31 December 2029, for processing started before the amendment). **Whether Abs. 2 and 2bis concern only federal bodies could not be confirmed from the synopsis** (in [I4], Abs. 2 is the federal-body paragraph).
- Reused, not re-read: DSG Art. 5 lit. h and Art. 24 (breach of data security and notification), [S1] in D-1 (12:55); DSG Art. 9 and 16, the Supabase DPA (Supabase Pte. Ltd, SCCs with Swiss addendum) and the Data Residency FAQ, [H3], [H4] in D-2 (13:50); DSG Art. 6 Abs. 4 and OR Art. 328b ([R2]) in D-4 (08:05).

**What each option processes**
- All options: the invited person's e-mail address, display name, role and, optionally, team and qualification label (staff data, not health data; [I3] applies, [I4] does not on these data alone). In B, C and D Supabase Auth (processor) sends an e-mail to that address. In A a NAVORA operator does the same by hand in the dashboard, which is the same processor and the same data, plus one more person with full dashboard access.
- B and C add a credential that **bypasses row-level security on the whole database**, including client health data once real data exist. That is the legally relevant difference: not the invitation, but what a stolen or misused key could reach.

**Settled (on the sources read)**
- **Sending an invitation e-mail is an ordinary processing of staff data.** Inviting a colleague to a work tool serves the employment or engagement ([R2] OR Art. 328b: data about suitability for or needed to perform the employment contract, reused). No source read forbids it or requires the person's consent to receive an invitation.
- **The information duty applies, and the invitation e-mail is the latest point.** The data come from the inviting administrator or team member, not from the person ([I1] Abs. 1, 3). Supabase receives them as soon as the invitation is sent, which is a disclosure to a processor, so the information is due at the latest then ([I1] Abs. 5). Minimum content: who the controller is and how to reach it, the purpose, the recipients (Supabase as processor), the categories of data (name, e-mail, role, team, qualification label), and, because Supabase processes support, account and incident data in Singapore and the US under SCCs (D-2 [H3], [H4]), the states and the guarantee ([I1] Abs. 2-4). A link in the e-mail to a privacy notice that states these points meets it; the first sign-in can repeat it. Art. 20 Abs. 1 lit. a ([I2]) removes the duty only where the person already has this information, for example from the employer's staff privacy notice; that depends on the licence holder's policy (D-12), so it cannot be assumed.
- **Who is the controller decides whose name the e-mail carries.** In staging with test accounts: NAVORA (the owner). With real teams: the organisation that employs or engages the members, with NAVORA as its processor (D-12 option B: the partner; D-12 conditions, `lca` 09:53). The e-mail must name that controller, not only "NAVORA".
- **Holding the key is a data-security measure under DSG Art. 8 ([I3]).** The law requires risk-appropriate measures; it prescribes no specific design. B, C and D are all designs that can meet it; which is appropriate is weighed against what the key reaches. No source read requires the owner, as a person, to approve a data-security design. The owner's role here comes from the repository rules (COORDINATION rule 5: production secrets), not from the DSG.
- **If the key leaks while real data exist, that is a breach of data security** (DSG Art. 5 lit. h, reused from D-1 [S1]): data "zugänglich gemacht" to an unauthorised party, with a notification to the EDÖB where a high risk results (Art. 24). A key that reaches all client health data makes a high risk plausible. This is why the design matters before real data, not before staging.
- **Logging.** An invite through the service role is not tied to a user's JWT, so the database cannot see who acted unless the app records it. The package already plans an audit row per call. Whether DSV Art. 4 logging is mandatory for NAVORA's production (sensitive data "in grossem Umfang") is UNKNOWN (see below), but recording who invited whom, when, with what result, is what [I4] Abs. 4 describes and is protective either way.

**UNKNOWN**
- Whether NAVORA's production processing is "large scale" under DSV Art. 4 Abs. 1 ([I4]), which would make logging of reads and disclosures mandatory, with logs kept a year separately from the system. It depends on the number of clients and organisations (D-11, D-12). The written review of logging ([I5] Abs. 2bis) could not be confirmed as applying to private controllers.
- Which mail provider Supabase uses to send Auth e-mails, and where (not read). If it is outside the adequacy list, [I1] Abs. 4 also needs that state in the notice. `eng` or the owner can read it from Supabase's sub-processor list.
- How long the e-mail address of a person who never accepted may be kept (question 4). DSG Art. 6 Abs. 4 (reused from D-4) requires deletion or anonymisation once the data are no longer needed for the purpose. A short period after expiry or revocation is plausibly justified (proof of who invited whom; abuse review). The audit row created by the trigger keeps the address under D-4's provisional rule (no deletion before the final periods). No source read sets a period. This is a D-4 retention criterion, not a period `lca` can set.

**Options**
- **A (manual creation): compliant under every plausible interpretation** on the sources read, under the same information duty (the operator's invitation e-mail also needs [I1] content). It concentrates full dashboard access in operators, which is a data-security weakness of its own, not a legal breach.
- **B (key on the app server, invite call only): compliant under every plausible interpretation for staging with synthetic client data**, under conditions (i)-(v) below. **For production with health data: unresolved: needs owner** (the residual-risk acceptance of a credential that reaches all health data from the app host), not because a source forbids it, but because whether it is "risk-appropriate" ([I3]) depends on facts not yet known (hosting, D-2; the host's access controls; volume, D-11). No legal adviser question is needed for staging.
- **C (Edge Function holds the key; the app calls it with the user's JWT; the function checks the open invitation row): compliant under every plausible interpretation for staging**, under (i)-(v); **for production the most protective of B and C**, because the key never reaches the Next.js host and the function can refuse anything but "send this open invitation". It does not change the processor or transfer position of D-2: the function runs inside the same Supabase project and region (question 2: **no change**, on D-2 [H3], [H4]; to be confirmed by `eng` that Edge Functions run in the project's region).
- **D (restricted sign-up, no privileged key): compliant under every plausible interpretation** on the sources read, if the hook reliably refuses sign-up without an open invitation (`eng`). Its failure mode (a hook that fails open lets anyone create an account) is a data-security question; it adds no legal question.
- **Conditions for B or C (all testable, none needs a legal adviser):**
  - (i) The invitation e-mail and the first sign-in show: the controller's name and contact, the purpose (access to the team's work tool), the recipients (Supabase as processor), the categories of data, and the states outside Switzerland/EU (Singapore, US) with the guarantee (SCCs), or a link to a notice that does ([I1] Abs. 2-5). The e-mail never contains client data or a qualification statement about the person.
  - (ii) The key sends invitations only for an open, unexpired invitation row, and nothing else; every call writes an audit row (who, which invitation, result, time), not the key and not the request headers.
  - (iii) No real client data in any project that holds the key until the production design is approved (D-1, D-2, the real-data gates of D-3, D-9, D-29).
  - (iv) The key is rotated on a recorded date and immediately if a leak is suspected; a suspected leak with real data is handled as a possible breach (Art. 24, D-1's procedure).
  - (v) An expired or revoked invitation is removed from the active table on a criterion written into D-4's retention criteria (not a period set here); the audit row follows D-4.
- **Who may invite** (later a team member, D-20): no new legal question beyond D-20 (18:47): the team decides membership; the employer records the contract fact once. The invitation does not make the person an employee; it must not suggest an employment offer.

**Verdict on the PO working view** (C if about the cost of B, otherwise B; staging only until D-1 and D-2; invite only from an open row; audited; rate-limited; e-mail naming NAVORA, the organisation and what is stored): **compliant under every plausible interpretation for staging**, provided conditions (i)-(v); the e-mail must name the **controller** (with real teams, the organisation, not NAVORA alone) and the **foreign states and guarantee** ([I1] Abs. 4), which the working view does not yet say. **For production: unresolved: needs owner** (residual-risk acceptance of the key's reach under DSG Art. 8, once D-2 hosting and D-12 controllership are known); C is the more protective design.

**Answers to the four questions:** (1) Yes, under (i): the e-mail is the latest point for the information; consent is not needed. (2) No option changes the D-2 processor or transfer position (C to be confirmed as running in-region); the mail sender's location is UNKNOWN and belongs in the notice. (3) A technical measure within the PO's authority for staging; for production a residual-risk acceptance by the owner, alongside rule 5. (4) No period on the sources read; a D-4 criterion, with Art. 6 Abs. 4 as the limit.

**Note to po:** (1) Write conditions (i)-(v) into the D-26 design; none needs a legal adviser. ## Risks and mitigations
| Risk | Mitigation |
|---|---|
| The key leaks to a browser or a log | server-only module, a build check that fails if the key name appears in client output, no logging of the request headers (`eng` to confirm) |
| A server flaw uses the key for reads or writes beyond invitations | one call only (B) or no key on the app host at all (C, D); every call audited; the database stays the authority (RLS unchanged for all other paths) |
| Invitation spam or enumeration | rate limit per organisation; only an open, unexpired invitation row can be sent; result codes do not reveal whether an account exists |
| A team invites someone without verified qualification who is then planned | qualification stays a label until D-29's gate; no real client before D-29 |
| The key is set on the live project | staging only until D-1 and D-2; the owner sets production secrets (rule 5) |
