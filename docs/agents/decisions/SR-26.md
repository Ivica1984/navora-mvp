# SR-26 — Foreign `orders` table in the live database

## Decision summary
The live NAVORA Supabase project also holds `public.orders` from another application: 10 Stripe test-mode checkouts with e-mail addresses (VERIFIED by schema and counts, 2026-10-21; the owning app is inferred). Should it be moved to that app's own project and then deleted from NAVORA's, deleted outright, or left contained? The PO's first triage: removing it is an irreversible change to a live database, so only the owner may execute it. **Preliminary route: `owner`.** Inputs requested: Engineering, Legal & Compliance. No clinical input needed.

## Context and problem statement
- **VERIFIED:** `engineering/SECURITY_RISKS.md` SR-26 (Medium, OPEN — owner): mixed purposes in one database break data minimisation and widen the impact of any NAVORA access flaw. Containment C-1 removed anon access to `orders` too (10 of 10 tables). The repository's migrations do not create `orders` (ADR-022: the repository schema is the target), so a future deploy from this repository would not manage it.
- **Not known:** which application owns `orders`, whether it still writes to this project, and whether the e-mail addresses are test or real people's (Stripe test mode says nothing about whose e-mails were typed in).
- **Link:** D-1 (same live project; the D-1 answer and the key rotation also cover this table).
- **Safe default in force:** contained (anon has no access); no agent touches the live project.

## Options considered
| Option | What it means | For | Against |
|---|---|---|---|
| A | Owner moves `orders` to the other app's own project (if it is still used), verifies the copy, then deletes it from NAVORA's project | one purpose per database; nothing lost | two projects to touch; the owner must know the other app |
| B | Owner deletes `orders` (after a private export kept outside the repository, if wanted) | simplest; minimisation | irreversible; breaks the other app if it still writes here |
| C | Leave it contained | nothing to do | SR-26 stays open; personal data with no NAVORA purpose stay in a health-data project |

## Engineering impact
*requested 2026-10-24 (po).* Asked: whether anything in this repository or its CI reads `orders` (expected: nothing); read-only checks the owner can run to see whether the other app still writes to it (latest row timestamp, without contents); a step list for A and B with a verification query; whether removing it changes any advisor finding.

## Clinical impact
not needed: no care, documentation, quality or safety rule is involved.

## Legal/compliance impact
*requested 2026-10-24 (po).* Involved because the table holds e-mail addresses (personal data) kept without a NAVORA purpose. Asked: whether keeping them contained (C) is compliant under every plausible interpretation (purpose limitation and minimisation, DSG Art. 6), whether deletion before the D-1 assessment could conflict with any duty, and whether the e-mail addresses widen any D-1 assessment.

## Risks and mitigations
| Risk | Mitigation |
|---|---|
| The other app still writes here and breaks | check the latest row timestamp first (A) |
| Deleted rows were needed for the D-1 assessment | delete only after D-1 is answered or cleared by `lca`/adviser |
| An agent deletes on the live project | rule 5: owner executes; agents write steps and read-only checks only |

## Recommended default for NAVORA
Pending inputs. **PO working view, not a decision:** **A**, done by the owner after D-1 is answered (or with `lca`'s clearance that deletion does not conflict), and in the same session as the D-1 key rotation. Until then: contained (C-1).
