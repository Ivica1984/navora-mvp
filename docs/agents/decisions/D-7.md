# D-7 — Branch protection, secret scanning, repository visibility

## Decision summary
Protect `main` and `recovery/main` (pull requests only, required CI checks, no force-push or deletion), switch on secret scanning with push protection, and decide whether the repository becomes private. The PO's first triage: protection and scanning are reversible governance controls with no cost while the repository is public; **visibility** is the hard part, because on a free personal account a private repository may lose free branch protection, free secret scanning and unlimited Actions minutes (to be confirmed by `eng`), which turns it into a paid-plan (owner) choice. **Preliminary route: `owner`** (production governance; settings writes are blocked for the agents, HTTP 403, so only the owner can execute). Inputs requested: Engineering, Legal & Compliance.

## Context and problem statement
- **Facts read by the PO through the GitHub API, 2026-10-24 11:09:** repository `public`; `main` and `recovery/main` **not protected**; secret scanning, push protection and Dependabot security updates **disabled**. PR #3 (`recovery/main` → `main`) open, mergeable.
- **Registers:** SR-14 (no protection, no required CI, no scanning; OPEN, owner), SR-18 (a public repository holds architecture, domain and security-gap documentation; OPEN, owner), SR-17 (no secrets found in the full history; CONTROLLED), SR-20 (bots excluded from the protected branches). Backlog O-A (rulesets), O-B (scanning).
- **What it blocks:** M2 (D-8: merge into `main`).
- **How the agents work today:** every change goes through a PR and is merged only with green CI by its role's agent (COORDINATION.md rule 4). A ruleset that requires `app`, `db` and `e2e` would make that rule technical rather than procedural.
- **No personal or health data in the repository** (README rule 8; synthetic test data only). The exposure is documentation of open security gaps and the full design.
- **Safe default in force:** agents merge only with green CI; no secrets in the repository.

**Sources (read 2026-10-24 by `lca`):**
- [P1] *Bundesgesetz über den Datenschutz (DSG)*, text for the final vote of 25 September 2020 (parlament.ch, Curia 17.059), read in this run: Art. 5 lit. h (breach of data security includes data becoming accessible to unauthorised persons); Art. 7 Abs. 1-2 (privacy by design: the controller designs the processing technically and organisationally **from the planning stage**, measures appropriate to the state of the art, the kind and extent of processing and the risk); Art. 8 Abs. 1-3 (controller **and processor** ensure data security appropriate to the risk by suitable technical and organisational measures; the measures must make it possible to avoid breaches; minimum requirements by ordinance); Art. 24 Abs. 1 (report to the FDPIC of a breach likely to cause a high risk). **The final-vote text, not the consolidated fedlex text (SR 235.1); the tool returned a summary, not the verbatim text.** I know of no amendment of these articles, but I did not check fedlex: UNKNOWN.
- [P2] Health Info Net AG, *Technische und organisatorische Massnahmen gemäss DSG/DSV*, V1.1, February 2026 (hin.ch), read in this run: a provider's summary of DSV Art. 3, including Abs. 2 lit. f (system security: known critical vulnerabilities are fixed) and Abs. 3 lit. c (breaches are detected quickly and mitigated). **Secondary source; DSV Art. 1-3 not read on fedlex.**
- Not read: DSV (SR 235.11) on fedlex; FDPIC guidance on source-code repositories or on the publication of security documentation (I found none); GitHub's plan terms (an `eng` fact, not a legal one); cantonal data-protection law (relevant only if a public body becomes a party, D-11).

**Settled (on the sources read)**
- The DSG applies to processing **personal data** ([P1]). A repository that holds code and documentation but no personal data is not itself a processing of personal data, so DSG Art. 8 does not apply to the repository as such.
- But the duties attach to the **system** the repository builds and describes: Art. 7 applies from the planning stage of the processing, and Art. 8 asks for security appropriate to the risk, including avoiding breaches ([P1]); health data are sensitive personal data, so the risk is high. Publishing a system's open security gaps is a factor in that risk assessment for **any environment that holds personal data**. No source read forbids a public repository or open source code; none read requires secrecy of a design ("security by obscurity" is not a measure the sources name).
- Whoever is the controller of the live database's contents (UNKNOWN, D-1 and D-12) carries the Art. 8 duty for it today, and the Art. 24 notification duty if a breach occurs.

**UNKNOWN**
- **Whether the live database holds real people's data (D-1).** This is the fact that decides the verdict on A. The public repository names the live project and documents its containment state and an unrotated key (SR-12). If the live data are real, the public documentation of that system's state is part of its exposure.
- Who the controller and processor are (D-12; NAVORA as a software provider is plausibly a processor of the future licence holder).
- The DSV wording on fedlex.

**Options**
- **A (rulesets and secret scanning with push protection; stay public until real data):**
  - *Rulesets and push protection:* measures that reduce risk; no legal objection on any source read. Push protection directly serves Art. 8 Abs. 2 (avoiding breaches through a leaked credential).
  - *Staying public:* **compliant under every plausible interpretation only while no environment described in the repository holds personal data.** That holds for the local and CI environments (synthetic data, README rule 8). It is **not shown** for the live project, because D-1 is open. So, as long as D-1 is open, **A is unresolved: needs owner** (the D-1 fact), and a legal adviser only if the live data turn out to be real.
- **B (A, then private before real data):** the more protective option; consistent with Art. 7 (from the planning stage) and with Art. 8 for the future controller. **Compliant under every plausible interpretation** on the sources read, as a security measure. It does not on its own make any future processing compliant (DSFA, processor contract, D-3 read scope remain).
- **C (private on the free plan):** compliant as to confidentiality; if it removes protection, scanning or CI (UNKNOWN, `eng`), it weakens integrity controls (DSV Art. 3 as summarised in [P2]: system security, detection). **Unresolved: needs `eng` facts**, not a legal adviser.
- **D (status quo):** **unresolved: needs owner (D-1)**; the least protective option, because push protection is missing (a committed secret is public at once).

**Missing facts and who supplies them:** D-1 (owner: real people in the live database or not; key rotation); D-12 (the controller); the plan terms (`eng`).

**Exact questions:**

If yes, the live project's identifier and security reports should not stay public while SR-12 is open, and a legal adviser should assess whether the past exposure is a breach under DSG Art. 5 lit. h that must be assessed under Art. 24.
2. (legal adviser, only if question 1 is "yes") Is the publication of a live system's containment state and open findings, without personal data, a breach of data security under Art. 5 lit. h, or only a risk factor under Art. 8?

**Verdicts:** rulesets and push protection: **compliant under every plausible interpretation**. Staying public (part of A): **unresolved: needs owner** (D-1); becomes compliant under every plausible interpretation once the owner confirms the live data are synthetic or deleted. B: **compliant under every plausible interpretation** as a measure. C: **unresolved: needs `eng` facts**. D: **unresolved: needs owner** (D-1).
