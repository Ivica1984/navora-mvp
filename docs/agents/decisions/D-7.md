# D-7 — Branch protection, secret scanning, repository visibility

## Decision summary
Protect `main` and `recovery/main` (pull requests only, required CI checks, no force-push or deletion), switch on secret scanning with push protection, and decide whether the repository becomes private. The PO's first triage: protection and scanning are reversible governance controls with no cost while the repository is public; **visibility** is the hard part, because on a free personal account a private repository may lose free branch protection, free secret scanning and unlimited Actions minutes (to be confirmed by `eng`), which turns it into a paid-plan (owner) choice. **Preliminary route: `owner`** (production governance; settings writes are blocked for the agents, HTTP 403, so only the owner can execute). Inputs requested: Engineering, Legal & Compliance.

## Context and problem statement
- **Facts read by the PO through the GitHub API, 2026-10-24 11:09:** repository `public`; `main` and `recovery/main` **not protected**; secret scanning, push protection and Dependabot security updates **disabled**. PR #3 (`recovery/main` → `main`) open, mergeable.
- **Registers:** SR-14 (no protection, no required CI, no scanning; OPEN, owner), SR-18 (a public repository holds architecture, domain and security-gap documentation; OPEN, owner), SR-17 (no secrets found in the full history; CONTROLLED), SR-20 (bots excluded from the protected branches). Backlog O-A (rulesets), O-B (scanning).
- **What it blocks:** M2 (D-8: merge into `main`).
- **How the agents work today:** every change goes through a PR and is merged only with green CI by its role's agent (COORDINATION.md rule 4). A ruleset that requires `app`, `db` and `e2e` would make that rule technical rather than procedural.
- **No personal or health data in the repository** (README rule 8; synthetic test data only). The exposure is documentation of open security gaps and the full design.
- **Safe default in force:** agents merge only with green CI; no secrets in the repository.

## Options considered
| Option | What it means | For | Against |
|---|---|---|---|
| A | Rulesets on both branches (PR only, required `app`, `db`, `e2e`, no force-push/deletion) + secret scanning and push protection; stay public for now | free; reversible; closes SR-14 at once | SR-18 stays open (security-gap docs public) |
| B | A, then private on a paid plan that keeps protection, scanning and enough Actions minutes | closes SR-14 and SR-18 | monthly cost (owner); plan terms to confirm |
| C | Private on the free plan | closes SR-18 | may lose free protection and scanning and limit Actions minutes (hourly agents), i.e. reopens SR-14 and can stop CI: UNKNOWN until confirmed |
| D | Status quo | nothing to do | SR-14 and SR-18 stay open |

## Legal/compliance impact
*requested 2026-10-24 (po).* Involved because it touches governance, security of a health-data system (data security duty) and the confidentiality of security documentation. Asked: whether a public repository without personal data but with documented open security gaps conflicts with any data-security duty of the future controller or processor (DSG Art. 8, DSV), and whether A (stay public) is compliant under every plausible interpretation until real data exist.

## Risks and mitigations
| Risk | Mitigation |
|---|---|
| A secret is committed and public at once | push protection (A) |
| Documented security gaps read by an attacker before real data exist | private (B) before any real data or live system is connected; no real data until then (existing gates) |
| A private switch on the free plan stops CI or protection | confirm plan terms first (`eng`); do not choose C blind |
| A ruleset blocks the agents' merges | required checks are the ones CI already runs; `eng` confirms names |
