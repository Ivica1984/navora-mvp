# D-8 — Merge `recovery/main` into `main`

## Decision summary
Merge PR #3 (`recovery/main` → `main`) with a merge commit, so that `main` holds the rebuilt NAVORA and the claude.ai Project, which syncs `main`, stops showing the old code. Gated in 2026-10-21 on D-7, the zip byte verification (O-C) and the Codespace check (O-D). The PO's first triage: a merge into the default branch is a production-branch change; history on `main` is permanent (a revert is possible, removal is not), so it is **`owner`**. The package asks whether O-C and O-D still gate it, since the code has been rebuilt and tested since. Inputs requested: Engineering, Legal & Compliance.

## Context and problem statement
- **Facts (GitHub API, 2026-10-24 11:09):** PR #3 open, `mergeable_state: clean`, 635 commits, 397 files; base `main` (default branch, not protected).
- **Why it matters:** the claude.ai Project syncs `main`, so every session reading the project sees the 2026-10-21 code and stale docs; agents work on `recovery/main`. Two sources of truth is coordination work and a source of errors.
- **Gates written 2026-10-21:** O-C (verify the transcribed import against the owner's zip; only on the owner's machine), O-D (preserve a Codespace if one exists), D-7 (protection), owner approval. SR-19: the recovered `src/` was a transcription; since then 60 migrations and most of the app were rebuilt under CI.
- **UNKNOWN:** whether anything is deployed from `main` (hosting, D-2); whether a Codespace exists (O-D).
- **Safe default in force:** `main` untouched; agents use `recovery/main`.

## Legal/compliance impact

Repository facts relied on (read, not tested): this package's *Context*; `docs/engineering/BACKLOG.md` O-C, O-D, M2; `docs/engineering/DECISIONS.md` (the transcription with per-file SHA-256 and `verify-against-zip.sh`); `docs/engineering/SECURITY_RISKS.md` SR-03, SR-19.

**Sources (read 2026-10-24 by `lca`, this run):**
- [S1] *DSG* of 25 September 2020, BBl 2020 7639 (copy of the fedlex publication PDF hosted by HSLU): Art. 5 lit. a; Art. 7 Abs. 1-2 (privacy by design from the planning stage, appropriate to the state of the art and the risk); Art. 8 Abs. 1-2 (controller and processor ensure security appropriate to the risk; measures must make it possible to avoid breaches); Art. 12 Abs. 1-2 (record of processing activities: identity, purpose, categories, recipients, retention, security measures). **Published 2020 text, not the consolidated fedlex text; extracts returned by the tool.**
- [S4] Kanton Zürich, Amt für Wirtschaft, Innovation Sandbox, *Besonderheiten bei Medizinprodukten* (zh.ch, dated 30 January 2026): software is a medical device under the MepV when its intended purpose, set by the manufacturer, is medical for individual persons (diagnosis, prevention, **monitoring**, prognosis, treatment); software limited to storage, archiving, simple search or communication generally is not; software that **summarises, prioritises or interprets clinical information** is named as a grey zone. **An orientation page, not the MepV or Swissmedic guidance; MepV not read.**

**Settled (on the sources read)**
- The DSG duties attach to the processing of personal data ([S1] Art. 5 lit. a, 7, 8). A code repository holding no personal data is not itself a processing, and no source read requires byte-level evidence of how source code was recovered, nor ties any record duty to it. The record of processing activities (Art. 12) describes processing, not code provenance.
- What Art. 7 and 8 do ask is that the system that **will** process health data is designed and secured appropriately from the planning stage. The relevant evidence for that is the reviewed, tested code and its history (on `recovery/main`, under CI), not identity with a pre-recovery archive. Dropping O-C as a merge gate therefore raises no data-protection question on the sources read, as long as the 2026-10-21 transcription stays identifiable in history (tag `preserve-*`, a merge commit).
- A merge becomes a data-protection question only if something deploys from `main` into an environment holding personal data (the live project, D-1): UNKNOWN, `eng`.

**UNKNOWN**
- **Whether NAVORA is a medical device** under the MepV. Its intended purpose is set by the manufacturer ([S4]). Parts of it raise, rank and route care exceptions and safety signals (CSR1, SIG1), which is close to the grey zone [S4] names. If NAVORA were a medical device, the manufacturer would owe technical documentation and traceability of released versions; the MepV text was not read, so the content of those duties is UNKNOWN. This question is **separate from D-8**: it would concern the documentation of what is released, not the pre-recovery zip, so it does not argue for keeping O-C.
- Whether anything deploys from `main` (D-2, `eng`), and whether a Codespace exists (O-D; no legal duty to keep it was found).

**Options**
- **A (merge now):** no data-protection objection on the sources read **if nothing deploys from `main`** into an environment with personal data; that fact is open. **Unresolved: needs `eng`** (deploy fact), not a legal adviser. Merging before D-7's protection is a governance risk, not a legal rule found.
- **B (after D-7 and O-D; O-C dropped if `eng` shows the transcription no longer matters):** **compliant under every plausible interpretation** of the data-protection sources read, provided nothing deploys from `main` into an environment holding personal data before D-1 is answered, and the transcription stays tagged.

- **D (wait):** no legal objection; the cost is coordination, not compliance.
